## 一、用户场景和需求描述

### 1.1 用户场景
1) 用户发起对话时，若某个模型不可用，系统应自动切换到候选模型，避免请求失败。  
2) 多议员与主席共用模型池时，任何单点故障不应导致全流程中断。  
3) 健康状态采用固定时间刷新机制，不因“每次新对话”而触发探测。  
4) 主席在 Stage3 也必须支持 fallback，避免最终总结阶段失败。  

### 1.2 需求描述
- 当模型失败时，自动切换到候选模型继续执行。  
- 仅“读取”健康状态做路由，不修改健康判定逻辑。  
- 议员不再绑定单模型，而是共享全局模型池。  
- 主席拥有独立的候选列表。  

### 1.3 非需求（明确不做）
- 不引入“全局主模型切换”的强制机制。  
- 不在每次会话创建/消息发送时强制刷新健康状态。  
- 不修改 health 判定算法的规则与阈值（仅调整刷新触发策略）。

## 三、决策与约束

### 3.1 决策（已确认）
| 项 | 决策 |
| --- | --- |
| unknown 是否可用 | 严格不可用 |
| 议员健康聚合 | 候选任一 healthy 即可用 |
| fallback 覆盖范围 | Stage1 / Stage2 / Stage3 全覆盖 |
| 主席候选列表 | 单独配置 |
| 全局主模型切换 | 不采用（按需选路） |

### 3.2 约束（必须满足）
- 不改 health 判定逻辑（阈值、失败归因、cooldown 机制保持现状）。  
- 健康刷新为“固定时间触发”，不在每次对话触发。  
- unknown 严格不可用，但需保证系统启动后仍可用。

## 四、现状与问题对齐

### 4.1 当前行为摘要
| 模块 | 当前行为 |
| --- | --- |
| 健康刷新 | 需显式触发（`refresh=true` 或启动开关） |
| 选路 | 每议员绑定单模型，不做候选 |
| 健康判定 | 模型维度，TTL + cooldown + hard failure |

### 4.2 现状问题
- unknown 严格不可用时，若无启动刷新，系统会“全不可用”。  
- 议员绑定单模型导致容错不足。  
- 主席阶段没有 fallback，Stage3 是单点失败。

## 五、详细技术方案

### 5.1 方案核心：按需选路（Option B）
- 全局维护健康缓存（Health Cache）。  
- 每次调用时按候选顺序选择第一个 healthy。  
- 不进行“全局主模型切换”。  
- 单次请求内使用 In-Flight Exclusion 临时排除失败模型。  

### 5.2 健康状态刷新策略（无歧义规则）
规则 1：**启动时必须立即刷新一次**  
规则 2：**之后每 1 小时刷新一次全量健康**  
规则 3：**每次模型调用成功/失败会更新健康状态（沿用现有逻辑）**  

注意事项：
- TTL 仅用于标记 stale，不代表自动刷新。  
- unknown 严格不可用，因此“启动即刷新”是必需条件。  

### 5.3 议员健康聚合规则
议员健康 = 候选列表中“任意模型 healthy”。  
若候选列表为空，视为不可用。  

### 5.4 主席健康规则
主席健康 = 主席候选列表中“任意模型 healthy”。  
主席候选列表与议员候选列表相互独立。  

### 5.5 In-Flight Exclusion 规则
In-Flight Exclusion 仅作用于“单次请求生命周期内”：  
1) 模型调用失败后将其加入本次请求的排除集合。  
2) 排除集合仅对当前请求生效，不影响全局健康状态。  
3) 下次请求仍基于健康缓存重新评估。  

### 5.6 重试与候选切换的优先级
为避免歧义，采用以下顺序：
1) 在候选列表中选择健康模型。  
2) 若调用失败，立即切换到下一个候选（同一请求内）。  
3) 不再对同一模型进行额外重试（除非既有逻辑硬性要求）。  
4) 候选耗尽则返回失败。  

> 说明：当前系统 Stage1/Stage2 已有固定重试机制。  
> 本方案不增加“额外重试次数”，避免调用量爆炸。  

### 5.7 模型级并发控制（可选增强）
- 在全局模型池中配置 `concurrency_limit`。  
- 每个模型独立信号量，避免 fallback 集中压垮单模型。  
- 当模型池规模较小、请求量低时，可暂缓实现。

## 六、详细流程（逐阶段）

### 6.1 Stage1（议员生成）
输入：用户问题 + 议员候选列表  
输出：每位议员的回答或失败对象  

**流程规则：**
1) 获取议员候选列表（按顺序）。  
2) 过滤出 `health_status == healthy` 的模型。  
3) 按顺序选择第一个 healthy 模型。  
4) 调用模型生成答案。  
5) 失败 -> In-Flight Exclusion -> 选下一个候选。  
6) 候选耗尽 -> 返回失败对象。  

**必需保证：**
- `unknown` 不可被选中。  
- 失败对象必须包含“失败原因”和“尝试过的模型列表”。  

### 6.2 Stage2（议员评审）
输入：Stage1 成功候选 >= 2  
输出：评审排序或跳过  

**流程规则：**
1) 若 Stage1 有效候选 < 2，则 Stage2 跳过。  
2) 对每个议员评审任务执行“候选选路”。  
3) 按候选顺序选健康模型，失败则切换。  
4) 候选耗尽 -> 该评审失败，但不影响其他评审。  

### 6.3 Stage3（主席总结）
输入：Stage1 + Stage2 结果  
输出：最终总结  

**流程规则：**
1) 主席候选列表独立获取。  
2) 选择第一个健康模型。  
3) 失败则切换下一个候选。  
4) 全部失败返回结构化错误。

## 七、状态机与边界条件

### 7.1 健康状态机（模型维度）
```
unknown --(probe success)--> healthy
unknown --(probe fail)-----> unhealthy or cooldown
healthy --(runtime fail)--> cooldown or unhealthy
cooldown --(time elapse)--> unknown
unhealthy --(probe success)--> healthy
```

### 7.2 边界条件清单
| 条件 | 处理规则 |
| --- | --- |
| 候选列表为空 | 直接失败，不尝试 |
| 健康缓存全是 unknown | 启动刷新必须确保可用 |
| Stage1 全部失败 | Stage2 跳过，Stage3 返回失败 |
| Stage2 全部评审失败 | Stage2 标记为跳过，Stage3 仍执行 |
| 主席候选全部失败 | Stage3 返回失败对象 |

## 十、需要改动的代码文件与关键修改点

> 注意：不写代码，仅列出需要改动的文件与关键点。

### 10.1 backend/config.py
- 增加 `GLOBAL_MODEL_POOL`。  
- 为每个议员/主席增加 `model_candidates`。  

### 10.2 backend/main.py
- 启动时立即触发一次全量刷新。  
- 启动后创建定时任务（每小时刷新）。  

### 10.3 backend/council.py
- Stage1/2/3 选路逻辑：按候选列表读取健康状态。  
- 单次请求内 In-Flight Exclusion。  
- 记录 `actual_model`、`attempted_models`。  

### 10.4 backend/health.py
- 不修改判定逻辑。  
- 确保 `get_status` 输出供选路器只读使用。  

### 10.5 backend/validation.py
- 不改探测逻辑，仅调整触发频率。

## 十三、风险与备选方案

### 13.1 风险
| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 启动未刷新 | 全部 unknown -> 不可用 | 强制启动刷新 |
| 候选列表过短 | fallback 无效 | 配置至少 2 个候选 |
| 单模型并发过高 | 触发限流 | 可选模型级并发控制 |

### 13.2 备选方案
| 方案 | 说明 | 不采用原因 |
| --- | --- | --- |
| 全局主模型切换 | 单次失败后全局切换 | 抖动与误判风险大 |
| unknown 可用 | 允许试探 | 与决策冲突 |

---

## 十四、实施步骤清单

1) 配置全局模型池与候选列表。  
2) 启动时触发刷新，确认健康缓存可用。  
3) 在 Stage1/2/3 添加选路逻辑与 In-Flight Exclusion。  
4) 记录实际使用模型与尝试列表。  
5) 添加定时任务每小时刷新健康状态。  
6) 执行验证矩阵中的测试场景。  

---

## 结论
本方案在严格 unknown 不可用的前提下，通过“启动即刷新 + 定时刷新”保证系统可用性；采用按需选路避免全局切换抖动；并在 Stage1/2/3 全覆盖 fallback，确保端到端可靠性。
