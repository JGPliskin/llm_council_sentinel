## 1. 项目背景与问题洞察（Why）

### 1.1 用户痛点（来自真实使用）

| 痛点 | 具体表现 |
|---|---|
| 选择困难 | 模型繁多，普通用户难以判断“哪个模型适合这个问题”。 |
| 答案单一 | 单模型回答缺少多元视角，易产生偏见或盲点。 |
| 质量不稳定 | 单模型有时“幻觉”，缺乏交叉验证机制。 |
| 难以评估 | 用户缺少评判标准，无法验证答案可信度。 |

### 1.2 设计洞察（核心假设）

> **核心假设**：多个模型的“集体智慧”优于单一模型的输出。  
> 类比现实中的 **陪审团、董事会、同行评审**：多方审议能提升决策可靠性。

## 2. 产品定位与核心理念（What）

### 2.1 一句话定位

> **LLM Council**：让多个 AI 组成“虚拟委员会”，通过协作、互评、综合来回答用户问题的智能决策助手。

### 2.2 核心理念对比（无歧义）

```
┌─────────────────────────────────────────────────────────────┐
│                  传统单模型对话                              │
│  User ──问题──► [单一模型] ──回答──► User                   │
│                        单一视角                              │
└─────────────────────────────────────────────────────────────┘

                          ▼ 升级为

┌─────────────────────────────────────────────────────────────┐
│                   LLM Council 模式                           │
│                                                              │
│  User ──问题──► [Councilor A][Councilor B][Councilor C]      │
│                     ↓          ↓          ↓                  │
│                  Stage 1：各抒己见                            │
│                     ↓          ↓          ↓                  │
│                  Stage 2：匿名互评                            │
│                          ↓                                   │
│                    Stage 3：主席综合                          │
│                          ↓                                   │
│                 User ◄── 多视角综合答案                       │
└─────────────────────────────────────────────────────────────┘
```

### 2.3 差异化价值（清晰对比）

| 维度 | 传统 AI 对话 | LLM Council |
|---|---|---|
| 答案来源 | 单一模型 | 多模型并行 |
| 评估机制 | 无 | 同行匿名评审 |
| 输出结构 | 单一回复 | 三阶段结构化输出 |
| 可信度 | 不透明 | 排名 + 评审理由可见 |
| 体验 | 一次生成 | 增量展示，过程可见 |

## 3. 目标用户与使用场景（Who）

### 3.1 用户画像

| 用户类型 | 特征 | 典型需求 |
|---|---|---|
| 决策者 | 需要在复杂问题上做判断 | “该选 A 还是 B？” |
| 学习者 | 希望获得多视角理解 | “不同观点怎么想？” |
| 研究者 | 需要综合多方观点 | “共识与分歧是什么？” |
| AI 探索者 | 对比评估模型能力 | “谁回答更好？” |

### 3.2 使用场景
1. 决策咨询：职业选择、投资决策、技术选型。  
2. 观点综合：复杂问题的多角度分析。  
3. 答案验证：通过交叉评审提高可信度。  
4. 模型对比：观察不同模型的思考差异。

## 4. 核心功能设计（How）

### 4.1 三阶段协作流程（产品核心）

**Stage1：初始观点（Proposal）**  
**输入**：用户问题 `content`（最大 1000 字符）  
**LLM 输出（每位 councilor 一次，严格 JSON）**：
```json
{
  "councilor_id": "string",
  "answer_markdown": "string",
  "answer_summary": "string (<=500 chars)",
  "judge_card": {
    "stance": "string",
    "core_reasons": ["string", "string"],
    "assumptions": ["string"],
    "risks": ["string"],
    "actionables": ["string"]
  }
}
```
**后端标准化后的 Stage1Result（写入会话）**：
```json
{
  "councilor_id": "...",
  "councilor_name": "...",
  "model": "...",
  "status": "ok|failed",
  "answer_markdown": "...",
  "answer_summary": "...",
  "judge_card": { ... },
  "attempted_models": ["..."],
  "fallback_used": true
}
```
**设计原因**：  
- `answer_summary` 降低 Stage2 token 消耗，确保评审聚焦核心观点。  
- `judge_card` 强制结构化“立场/理由/风险/行动”，便于比较。  

**Stage2：匿名互评（Peer Review）**  
**触发条件**：Stage1 有效候选 **>= 2**，否则跳过。  
**匿名机制**：后端生成 `anon_map`（如 `anon_1 -> councilor_id`），评审时隐藏真实身份。  
**输入**：每个候选仅包含 `answer_summary + judge_card`。  
**LLM 输出（每位 judge 一次，严格 JSON，字段集合必须等于允许集合）**：
```json
{
  "ranking": ["anon_1", "anon_2", "anon_3"],
  "scores": { "anon_1": 8, "anon_2": 6 },
  "rationale": "string"
}
```
**后端标准化后的 Stage2Review（写入会话）**：
```json
{
  "judge_councilor_id": "...",
  "judge_councilor_name": "...",
  "model": "...",
  "ranking": ["anon_1", "anon_2"],
  "scores": { "anon_1": 8, "anon_2": 6 },
  "rationale": "..."
}
```
**硬约束**：  
- `ranking` 必须覆盖全部 `anon_id` 且无重复。  
- `scores`（可选）必须 1–10 整数且仅包含 `anon_id`。  
- 任何额外字段、markdown、解释文本均视为无效。  

**Stage3：主席综合（Consensus）**  
**输入**：Stage1 全部答案 + Stage2 排名结果  
**输出**：
```json
{
  "status": "ok|failed",
  "model": "string",
  "response": "<markdown>",
  "attempted_models": ["..."],
  "fallback_used": false
}
```
**触发条件**：除非 Stage1 全部失败，否则始终执行。

### 4.2 角色与人格化设计（体验差异化）

**Councilor / Chairman 配置字段（来自 `backend/config.py`）**：
```text
id, name, avatar,
model, model_candidates[],
persona_path, judge_persona_path,
judge_system_prompt, stage_limits
```

**人格化的产品原则（不可违反）**：
- 人格必须体现在 Prompt 中，影响输出风格。  
- 人格只影响内容风格，不得改变 JSON 结构或字段名。  

**头像展示规则**（UI 必须遵守）：  
- 主标签为 `avatar + name`。  
- 模型名仅做 tooltip/次要信息。  
- `avatar` 允许 Emoji 或图片 URL，缺失时前端 fallback。  

---

### 4.3 模型健康与回退（可靠性设计）

**健康状态**：`healthy / degraded / unhealthy / unknown`  
**关键规则（现状 + 规范一致）**：  
- `healthy == True` 才可执行；`unknown` **严格不可用**。  
- 硬失败（401/403/404）直接标记不可用。  
- 失败达到阈值进入冷却（backoff）。  

**回退机制（Fallback Routing）**：  
1. 优先使用 `model`，若不健康则按 `model_candidates` 顺序回退。  
2. 单次请求内失败模型加入“排除集合”，继续尝试下一个候选。  
3. 候选耗尽则返回失败对象。  
4. Stage1 / Stage2 / Stage3 全覆盖回退逻辑。  

**透明输出字段（便于排障）**：  
- `attempted_models`：本次尝试过的模型列表。  
- `fallback_used`：是否触发回退。  

---

### 4.4 思考流展示（可选增强功能）

**功能目的**：长时间等待时给用户“可见进度”，降低焦虑。  
**触发条件**：  
- 请求体包含 `enable_thinking: true`（前端变量名 `enableThinking`，后端字段名 `enable_thinking`）。  
- 模型在 `GLOBAL_MODEL_POOL` 中标记 `capabilities.thinking == True`。  

**SSE thinking 事件（现状定义）**：
```json
{
  "type": "thinking",
  "stage": "stage1|stage2|stage3",
  "councilor_id": "...",
  "model": "...",
  "delta": "<title>",
  "is_title": true,
  "t": 1.23
}
```

**边界约束**：  
- thinking 事件 **仅用于 UI 实时展示**，不写入会话存储。  
- 对不支持 thinking 的模型必须平滑降级（正常输出答案，不报错）。  
- 现状：空白态输入区没有 thinking toggle（见 `docs/AGENTS.md`）。  

> 注：`docs/THINKING_STREAM_SPEC.md` 还定义了 UI/性能规范（如批量渲染、胶囊 UI）。若与当前实现不一致，以代码实现为准并另行规划。

---

### 4.5 会话与存储（数据一致性）

**存储位置**：`data/conversations/{conversation_id}.json`  
**核心字段**（节选，完整结构见 `docs/AGENTS.md`）：
```json
{
  "id": "<uuid>",
  "created_at": "<iso8601>",
  "title": "<string>",
  "messages": [
    { "role": "user", "content": "<string>" },
    {
      "role": "assistant",
      "stage1": [ { ... } ],
      "stage2": { ... },
      "stage3": { ... },
      "metadata": {
        "anon_to_councilor": { "anon_1": "councilor_id" },
        "aggregate_rankings": [ ... ],
        "spec_version": "stage2_v1.2"
      }
    }
  ],
  "active_councilor_ids": ["id1", "id2"],
  "active_chairman": "chairman_id",
  "schema_version": 2
}
```
**重要原则**：  
- 仅保存最终 `assistant` 消息；中间增量结果不落盘。  
- thinking 标题不持久化。

## 5. 接口与协议（无歧义定义）

### 5.1 REST API（现状）
```
GET    /api/councilors?refresh=<bool>
POST   /api/conversations
GET    /api/conversations
GET    /api/conversations/{id}
POST   /api/conversations/{id}/message
POST   /api/conversations/{id}/message/stream
DELETE /api/conversations/{id}
POST   /api/conversations/bulk-delete
```

### 5.2 SSE 事件序列（现状）
```
meta
stage1_start → stage1_item* → stage1_complete
stage2_start → stage2_item* → stage2_complete
stage3_start → stage3_complete
title_complete (仅首条消息)
complete
```

**关键 payload 规则**：  
- `meta`：包含 `resolved_councilor_ids`、`ignored_ids`、`councilors[]`、`chairman`。  
- `stage2_start`：一次性下发 `anon_map`。  
- `stage1_item` / `stage2_item`：单人结果，含 `status(ok/failed)` 与 `error`。

## 6. UX 交互设计要点（体验落地）

### 6.1 信息层级与布局（ASCII 原型）
```
┌──────────────────────────────────────────────────────────┐
│ COUNCIL MEMBERS（头像+姓名，实时状态）                    │
│ [?? 康德 ?]  [?? 特朗普 …]  [?? 小岛秀夫 ?]               │
├──────────────────────────────────────────────────────────┤
│ STAGE 1：初始观点（Tab 增量出现）                         │
│ [康德] [特朗普] [小岛]                                    │
│ 当前 Tab 的完整回答                                       │
├──────────────────────────────────────────────────────────┤
│ STAGE 2：评审排名（实名 + 头像 + 进度条）                 │
│ 进度 2/3 [███████???] 66%                                 │
│ 排名：??康德  ??小岛  ??特朗普                            │
├──────────────────────────────────────────────────────────┤
│ STAGE 3：最终答案                                         │
│ 主席综合后的最终建议                                     │
└──────────────────────────────────────────────────────────┘
```

### 6.2 关键交互规则
- **增量展示**：Stage1/2 谁先完成谁先展示，不等待全部完成。  
- **实名展示**：Stage2 排名必须通过 `anon_map` 映射成 `avatar + name`。  
- **进度条**：  
  - Stage1 total = `meta.resolved_councilor_ids.length`  
  - Stage1 done = `stage1_item` 计数（ok/failed 都算）  
  - Stage2 total = Stage1 total  
  - Stage2 done = `stage2_item` 计数  
- **Thinking 切换**：若 UI 存在 Toggle，则开关仅影响是否发送/渲染 thinking 事件，不影响回答本身。

## 8. 明确不做的事（Non-Goals）

| 不做的事 | 原因 |
|---|---|
| 多轮上下文深度对话 | 三阶段流程已足够复杂，MVP 聚焦一次问答。 |
| 中间态落盘/断线恢复 | 实现复杂度高，收益不成比例。 |
| 自动解析 `reasoning_content` | 规范明确依赖 `emit_thinking_title` 工具调用。 |
| 全局主模型切换 | 可能引发系统抖动，违背回退设计原则。 |
| 数据库持久化 | MVP 阶段 JSON 文件存储足够。 |

## 10. 验收标准（无歧义）

**流程类**  
- Stage1/Stage2/Stage3 均可触发，Stage2 在有效候选 < 2 时必须跳过。  
- 增量展示必须真实：先完成者先显示。  

**数据类**  
- Stage1 输出含 `answer_summary` 且长度 ≤ 500。  
- Stage2 输出严格 JSON：仅 `ranking/scores/rationale` 三个字段。  
- `ranking` 覆盖全部 `anon_id` 且无重复。  

**体验类**  
- Council Members 主标签为 `avatar + name`。  
- Stage2 排名实名化（通过 `anon_map`）。  
- Stage1/Stage2 进度条随 `stage*_item` 更新。  

**稳定性类**  
- 不健康模型不可被选中，候选回退可用。  
- thinking 开关关闭时不产生 thinking 事件。

## 11. 风险与对策（PM 必须提前说明）

| 风险 | 影响 | 对策 |
|---|---|---|
| 模型不可用 | Stage1/2/3 失败 | 健康检测 + 回退候选 |
| 模型输出格式错误 | Stage2 解析失败 | 严格 JSON Guard + 策略性重试 |
| 并发高导致延迟 | 用户等待过长 | 并发上限 + SSE 增量 + Thinking 提示 |
| 用户无法理解差异 | 体验模糊 | 头像/人格化 + 排名 + 进度可视化 |

---

## 12. 给新手 PM 的建议（可操作）

1. **从问题出发**：明确“用户为什么需要多模型协作”。  
2. **把流程拆清楚**：每个阶段的输入、输出、约束写到字段级。  
3. **先定义 Non‑Goals**：避免范围膨胀。  
4. **写清验收标准**：让研发和 QA 有“是否完成”的统一标准。  
5. **异常路径优先**：失败场景越明确，产品越稳定。  

---

## 结语

LLM Council Sentinel 的核心价值在于：  
**用结构化、多视角、可评审的机制，替代单模型的“单点答案”。**  

这份复盘强调“可复现”和“无歧义”，新手 PM 只要按本文步骤拆解，就能复刻出同样的产品设计过程。
