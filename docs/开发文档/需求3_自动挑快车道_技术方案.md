# 需求3：自动挑快车道（TTFT 优先路由）技术方案

> 目标：让系统在 Stage1 阶段自动选择“首字更快”的模型，将 TTFT 从 ~9s 降到 1–2s 的体验区间。  
> 原则：轻量实现、仅后台管理员可控、仅 Stage1 生效、无需频繁刷新、避免抖动。

## 1. 用户场景与需求描述

### 1.1 用户场景
- 用户希望系统在 Stage1 输出时“首字更快”。  
- 当前系统只看健康状态，不看速度：只要模型健康，即使 TTFT 很慢也会被选中。  
- 需要自动“挑快车道”，动态切换速度更快的候选模型。

### 1.2 需求描述（无歧义）
1) **速度排序**：按 TTFT 由快到慢排序，默认选最快。  
2) **管理员可开关自动选路**：当 `auto_route_by_speed = false` 时，严格按 `model_candidates` 顺序选第一个健康模型。  
3) **速度来源**：仅使用健康探测时的 TTFT（每 2 小时刷新）。  
4) **异常慢触发**：运行中若异常慢，触发一次“候选集紧急探测”，用于更新排序。  
5) **防抖切换**：切换需满足“双阈值”条件，避免频繁抖动。  
6) **范围**：只对 Stage1 生效；Stage2/3 维持现状。  
7) **用户可选 Councilor**：`councilor_ids` 仍可用，不涉及模型顺序。

## 2. 术语与范围

### 2.1 术语
| 术语 | 定义 |
| --- | --- |
| TTFT | Time To First Token，首字等待时间 |
| 健康探测 | 后台定时探测模型是否可用 |
| EMA | 指数滑动平均，平滑 TTFT |
| p50 | 中位数，抗极值 |
| auto_route_by_speed | 是否启用速度排序（管理员开关） |
| model_candidates | 候选模型池，包含稳定顺序（仅 tie-breaker） |

### 2.2 范围
- **仅 Stage1**：只影响 Stage1 选路。  
- **不影响 Stage2/3**：Stage2/3 继续按原有健康顺序。  
- **仅后台管理员**：不提供前台/用户排序入口。  
- **保留用户选择 Councilor**：`councilor_ids` 仍可用。

| 项 | 决策 |

| 自动选路开关 | `auto_route_by_speed`（默认 true） |

| 排序指标 | EMA / p50（p50 为 best-effort） |

| 当前首选记忆 | 仅内存态（重启即重置） |
| 紧急探测时段 | 可绕过时段限制，仍受冷却 |

## 4. 详细技术方案

### 4.1 路由模式
路由分两种模式，按 `auto_route_by_speed` 执行：

- **auto_route_by_speed = false**  
  严格按 `model_candidates` 顺序，选择第一个健康模型。  

- **auto_route_by_speed = true**  
  按 TTFT 速度排序选最快模型。

自动速度模式的**稳定性规则**：
- 若多个模型速度相同，或速度缺失，则使用 `model_candidates` 的原始顺序作为 tie-breaker。  
- `model_candidates` 因此具备“稳定顺序”的含义，但**不代表优先级**（优先级由速度决定）。

### 4.2 自动速度排序指标（无歧义定义）
排序指标的选择优先级：
1) `p50_ttft_ms`（仅当样本数 ≥ 5）  
2) `ema_ttft_ms`  
3) `last_ttft_ms`  
4) **缺失 TTFT**（排最后）  

#### 4.2.1 指标计算公式
- **EMA**：  
  `EMA_t = alpha * TTFT_t + (1 - alpha) * EMA_{t-1}`  
  其中 `alpha = 0.3`，`TTFT_t` 为本次探测的 TTFT。  
  若无历史 EMA，则 `EMA_0 = TTFT_0`。  

- **p50**：  
  取“最近 5 次健康探测 TTFT 样本”的中位数。  

- **last_ttft**：  
  最近一次健康探测 TTFT。  

#### 4.2.2 样本窗口与过期规则
- 样本仅来自**健康探测**（不使用运行时请求 TTFT 作为统计样本）。  
- 每个模型最多保留最近 **5** 个探测样本。  
- 若 `ttft_updated_at` 距当前超过 **6 小时**，视为缺失 TTFT（排序时排最后）。

#### 4.2.3 p50 的实际作用说明
- 探测周期为 2 小时，5 个样本约需 10 小时积累。  
- 在系统刚重启或运行初期，p50 多数不可用，因此**EMA 是常态指标**。  
- 文档明确：p50 为 best-effort（锦上添花），不是核心依赖。

### 4.3 防抖切换（双阈值）
自动速度模式下，切换需同时满足双阈值，避免因轻微抖动频繁切换。

**对比对象定义**：
- `current`：当前 councilor 的“内存态首选模型”。  
- `top`：按速度排序后的第一名候选模型。  
- `current_ttft` 与 `top_ttft` 均按 4.2 的“指标优先级”计算。

**切换规则**：
1) 若 `current` 不存在、已不健康、或 TTFT 缺失/过期，则直接选 `top`。  
2) 若 `current == top`，保持不变。  
3) 否则计算：  
   - `abs_diff = current_ttft - top_ttft`  
   - `rel_diff = abs_diff / current_ttft`  
   当且仅当 `abs_diff >= 800ms` 且 `rel_diff >= 30%` 时，切换为 `top`。  
4) 未满足阈值则保持 `current`。

### 4.4 异常慢触发（紧急探测）
运行中如发现 TTFT 异常慢，触发“候选集紧急探测”，用于刷新排序：
- 触发阈值：  
  - `TTFT >= 5000ms`  
  - 或 `TTFT >= EMA * 3`  
- 刷新范围：仅当前 councilor 的候选模型  
- 冷却时间：10 分钟（按 **model 维度**）  
- 可绕过时段限制（如 10:00–24:00）  

**紧急探测执行规则（按 model 冷却）**：
1) 遍历当前 councilor 的 `model_candidates`。  
2) 若某 model 在 10 分钟内已被紧急探测过，则跳过该 model。  
3) 仅对未被冷却的 model 发起探测。  
4) 若全部被冷却，紧急探测本次不执行。

**TTFT 测量口径（探测）**：
- 探测请求使用固定最小提示（例如 `Reply OK`）。  
- 以“请求发送”到“收到首个 token 或首个 tool_call”为 TTFT。  
- 若探测失败（超时/错误），本次不更新 TTFT 样本。

### 4.5 记忆策略
“当前首选模型”按 **councilor 维度**只保存在内存，重启后重置。  
该设计保持轻量，避免持久化带来的复杂度。

### 4.6 重启行为说明
- 重启后无 TTFT 数据：排序视为“全缺失”。  
- 行为：按 `model_candidates` 顺序选第一个健康模型。  
- 影响：首个请求可能仍慢；这是轻量化 trade-off。  
- 可选增强：启用一次性 startup 探测（不属于当前需求）。

## 5. 流程图与架构图

### 5.1 Stage1 选路流程（ASCII）
```
+------------------------------+
| Stage1 Request               |
+------------------------------+
           |
           v
   Filter healthy candidates
           |
           v
 auto_route_by_speed?
     | No  -> pick first healthy by model_candidates
     | Yes -> speed ranking (p50/EMA/last)
                 |
        pass switch threshold?
          | Yes -> pick fastest
          | No  -> keep current
```

### 5.2 异常慢触发流程（ASCII）
```
TTFT observed >= 5s OR >= EMA*3
          |
          v
  emergency probe (per-model cooldown)
          |
          v
for each model in candidates:
   if cooldown < 10min: skip
   else: probe model
```

### 5.3 逻辑架构（ASCII）
```
-------------------+      +---------------------+
| Stage1 Router     |----->| Health Cache + TTFT |
| (auto or config)  |      | (EMA/p50/last)      |
-------------------+      +---------------------+
            |                       |
            v                       v
        OpenRouter             Health Probes
```

## 6. 数据结构与字段规范

### 6.1 Councilor 配置（概念）
```
{
  id,
  model_candidates: [modelA, modelB, ...],  # 稳定顺序，仅用于 tie-breaker
  auto_route_by_speed: true | false         # 默认 true
}
```

### 6.2 HealthRecord 增量字段（概念）
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `last_ttft_ms` | number | 最近一次探测 TTFT |
| `ema_ttft_ms` | number | 平滑 TTFT |
| `p50_ttft_ms` | number | 中位数 TTFT |
| `ttft_samples` | number | 样本数量 |
| `ttft_updated_at` | string | 更新时间 |
| `last_emergency_probe_at` | string | 上次紧急探测时间（按 model 维度） |

### 6.3 RoutingState（内存态，概念）
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `current_model_by_councilor` | map | 每个 councilor 当前首选模型 |
| `last_selected_at` | map | 最后一次选路时间 |

## 7. 边界条件与异常处理

| 条件 | 处理规则 |
| --- | --- |
| auto_route_by_speed = false | 按 `model_candidates` 顺序选第一个健康 |
| 候选 TTFT 全缺失 | 按 `model_candidates` 顺序选第一个健康 |
| TTFT 过期（>6h） | 视为缺失，参与排序时排最后 |
| p50 样本不足 | 退回 EMA/last_ttft |
| 只有 1 个健康模型 | 直接使用 |
| Stage2/3 | 不应用速度排序 |
| 紧急探测全部命中冷却 | 本次紧急探测不执行 |
| 重启后首请求 | 可能回退到“按候选顺序”选路 |

## 8. 可观测性与验证

### 8.1 观测指标
| 指标 | 来源 |
| --- | --- |
| TTFT | `backend/logs/request.log` |
| 健康状态 | HealthManager 内存状态 |
| 选路结果 | Stage1 实际使用模型 |

### 8.2 选路决策日志（可选增强）
建议在 `request.log` 中增加选路原因字段，便于排查：

```json
{
  "routing": {
    "mode": "auto_speed" | "config_order",
    "candidates_ttft": {
      "mimo": 3200,
      "nemotron-9b": 1800,
      "nemotron-30b": null
    },
    "selected": "nemotron-9b",
    "reason": "fastest_healthy"
  }
}
```

### 8.3 验证场景
| 场景 | 预期 |
| --- | --- |
| auto_route_by_speed=false | 按候选顺序选第一个健康 |
| auto_route_by_speed=true | 按速度排序选最快 |
| TTFT 缺失 | 排最后 |
| TTFT 突然变慢 | 触发紧急探测（按 model 冷却） |
| 切换阈值不满足 | 保持当前首选 |
| 重启后首请求 | 按候选顺序选第一个健康 |
| Stage2/3 | 不受影响 |

## 9. 需要改动的代码文件与关键修改点

| 文件 | 关键修改点 |

## 10. 风险与备选方案

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 探测样本稀疏 | 排序不稳定 | p50 样本不足退回 EMA |
| 固定 2h 频率 | 滞后 | 异常慢触发紧急探测 |
| 切换过频 | 抖动 | 双阈值限制 |
| 重启丢失首选 | 首请求可能慢 | 轻量项目可接受 |

---

## 11. 范围外增强（非需求）
以下属于未来可选增强，不纳入当前实现范围：
- **模型温度惩罚**：记录 `last_actual_use_time`，冷模型 TTFT 加惩罚。  
- **运行时 TTFT 采样**：将真实请求 TTFT 作为辅助样本。  
- **启动强制探测**：startup 触发一次全量探测以减少首请求慢。

## 结论
本方案在不引入额外复杂度的前提下，实现 Stage1 “自动挑快车道”。  
规则清晰、可观测、具备异常慢处理与防抖机制，适配轻量项目与低并发场景。
